## 5. Codex Real Semantics

Inspection of the 33 sequential events from the real Codex session revealed the following empirical truths:

### 5.1 `last_token_usage` Nature
Is `payload.info.last_token_usage` cumulative, a single request delta, or a repeating snapshot?

- **`output_tokens` is a per-turn generation delta**:
  Across sequential events, output tokens fluctuate dynamically per turn:
  `244 -> 236 -> 356 -> 126 -> 100 -> 94 -> 200 -> 152 -> 341 -> 198 -> 210 -> 222 -> 232 -> 133 -> 102 -> 1445 -> 239 -> 429 -> 694 -> 2023 -> 1393 -> 174 -> 736 -> 185 -> 212 -> 219 -> 128 -> 177 -> 7724 -> 112 -> 134 -> 122 -> 122`.
  It does NOT accumulate monotonically. It directly measures the completion tokens generated by the LLM for that specific turn.
- **`reasoning_output_tokens` is a subset of `output_tokens`**:
  For all events, `reasoning_output_tokens <= output_tokens`. For example, in turn 16 (`output_tokens: 1445`), reasoning accounts for `1161` tokens. In turn 29 (`output_tokens: 7724`), reasoning accounts for `1506` tokens.
- **`input_tokens` is the active context length sent to the API for that turn**:
  Input tokens grow over the course of the session as conversation history accumulates:
  `22,480 -> 23,917 -> 24,163 -> ... -> 144,785 -> 152,932`.
- **`cached_input_tokens` is a subset of `input_tokens`**:
  Represents OpenAI prompt caching. For all events, `cached_input_tokens <= input_tokens`. For instance, on turn 28 (`input_tokens: 143,664`), `142,720` tokens were served from the prompt cache.
- **Token Invariant**:
  In 100% of the 33 observations:
  $$\text{input\_tokens} + \text{output\_tokens} = \text{total\_tokens}$$
  $$\text{cached\_input\_tokens} \le \text{input\_tokens}$$
  $$\text{reasoning\_output\_tokens} \le \text{output\_tokens}$$

### 5.2 Request Identity in Real Codex Logs
- In real Codex rollout session files, **neither `requestId` nor `request_id` is present on the event envelope**.
- Synthetic fixtures previously assumed `requestId: "req_..."`. In reality, Codex rollout events rely on file position and timestamps.
- Usage.ai's fallback in `parse_chunk_bytes`:
  ```rust
  let source_record_id = event
      .request_id
      .map(|id| format!("{path_hash}:request:{id}"))
      .unwrap_or_else(|| format!("{path_hash}:{record_offset}"));
  ```
  Because no request ID exists in raw logs, each line receives an offset-based ID.

### 5.3 Repeated Request Observations
- Lines 32 and 33 are identical in tokens (`in: 152932`, `cache: 151936`, `out: 122`, `reas: 34`, `tot: 153054`) and rate limits (`17%`), occurring 12 seconds apart (`18:03:49` and `18:04:01`).
- This proves that Codex session files can record duplicate flush events at session closure.
- In Usage.ai's storage model, re-importing the file atomically replaces the prior generation (`commit_import_batch`), preventing cross-import inflation. However, within a single file parse, adjacent identical offset records are imported as separate turns unless deduplicated by content/timestamp hashing.

### 5.4 Rate Limits
- Every `token_count` event carries real rate limit telemetry:
  - `primary`: 5-hour window (`window_minutes: 300`), tracking usage progression from `1%` up to `17%`, with exact Unix reset epoch `1788216217`.
  - `secondary`: 7-day window (`window_minutes: 10080`), tracking usage progression from `2%` up to `5%`, resets at `1788754169`.
  - `plan_type`: `"plus"`.
- Usage.ai parses both windows accurately into `Quota` structures.

## 9. Claude Real Semantics

Analysis of the 72 events across the real Claude Code session yielded crucial discoveries:

### 9.1 Logical Response Identity & Streaming Deduplication
- **1-to-1 Mapping**: Every `message.id` (`msg_0001`, `msg_0002`, ...) maps strictly 1-to-1 with a `requestId` (`req_0001`, `req_0002`, ...).
- **Streaming Multi-Emission**: Each logical model response is recorded **2 to 4 times** during streaming progress:
  - Example: `msg_0001` appears on lines 1, 2, 3, and 4 (timestamps `07:15:01.455` through `07:15:03.754`). Each line has a distinct `uuid` (`uuid_0001` through `uuid_0004`).
  - **In all observations of a given message, the token counters are identical final values** (`input: 2`, `output: 619`, `cache_creation: 25727`, `cache_read: 41410`).
- **Production Deduplication Match**:
  Usage.ai computes the record ID as:
  ```rust
  format!("msg:{msg}:{req}")
  ```
  All 4 observations of `msg_0001` yield the identical key `msg:msg_0001:req_0001`.
  Usage.ai's deduplicating storage / monotonic reducer collapses the 72 raw lines into exactly **27 unique logical responses**.
  **45 duplicate lines are eliminated cleanly with zero double counting**.

### 9.2 Cache Semantics
Anthropic / Claude Code API splits prompt tokens into three mutually exclusive buckets:
1. `input_tokens`: Non-cached prompt tokens (e.g. 2 tokens for user turn prefix).
2. `cache_creation_input_tokens`: Tokens written to Anthropic prompt cache on this turn (e.g. 25,727 tokens).
3. `cache_read_input_tokens`: Tokens retrieved from Anthropic prompt cache (e.g. 41,410 tokens).
4. `output_tokens`: Completion tokens generated (e.g. 619 tokens).

Total prompt context evaluated = $\text{input} + \text{cache\_creation} + \text{cache\_read} = 2 + 25,727 + 41,410 = 67,139$ tokens.
Net turn tokens = $67,139 + 619 = 67,758$ tokens.

Usage.ai's formula:
```rust
let total_tokens = input_tokens.unwrap_or(0)
    + output_tokens.unwrap_or(0)
    + cache_creation_tokens.unwrap_or(0)
    + cache_read_tokens.unwrap_or(0);
```
matches the official Anthropic API billing specification exactly.

### 9.3 Model Identity
- 100% of events specify `model: "claude-sonnet-5"`.
- The model field is stable per response and never missing.
