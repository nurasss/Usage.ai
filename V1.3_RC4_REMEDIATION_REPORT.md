## 3. Usage-total trust root cause

The provider DTO path is refresh_flow::attach_usage_and_cost -> usage_runtime::account_usage_and_cost_today -> ProviderDto.tokens_today. The old account token helper summed every row for an account/product without a coverage predicate. That raw behavior is useful for local history and diagnostics, but it was also used by the provider-facing DTO path, so Unknown, LocalClientOnly, and UnverifiedSemantics could inflate a provider total.

The ordinary overview/model/account/project SQL was already authoritative-only; the defect was the separate account/provider DTO path.

## 4. Cost-total trust root cause

The provider-facing daily DTO and costs_by_period aggregate read raw cost_records_between results. Their runtime loops previously summed records without requiring authoritative coverage. Non-authoritative amounts could therefore appear as provider-facing totals. The raw cost query remains broad for history and diagnostics; the existing budget-notification path already requires Coverage::is_authoritative().

## 5. Authoritative aggregation fix

The domain policy is unchanged: Coverage::Complete | Coverage::Partial is authoritative, and Partial was not globally reclassified.

The storage layer now exposes authoritative_tokens_for_account_between with SQL coverage IN ('Complete','Partial'). The raw tokens_for_account_between helper is unchanged. Both runtime provider-facing cost loops now require record.coverage.is_authoritative() plus matching account_id and product_id.

The authoritative usage query and runtime cost filters feed ProviderDto.tokens_today, reported_cost_today, estimated_cost_today, and costs_by_period; this is not a UI-only or tray-only filter.
